# Creating Plugins

## Introduction

Welcome! This guide walks you through building your first Graph plugin from scratch. By the end, you'll have a working node that adds two numbers — and you'll understand the fundamentals needed to build any kind of plugin.

Graph plugins are the building blocks of the Graph platform. They can be **datatypes** (defining what kinds of data flow through your graphs), **widgets** (providing UI for editing data), **nodes** (performing computations and transformations), or **utilities** (shared code imported by other plugins). In this tutorial, we'll focus on creating a node — the most common type of plugin you'll build.

<InlineAlert variant="info" slots="text"/>

**First time here?** You're in the right place. This is designed to be your first experience with Graph plugins. We'll build something real, explain every step, and show you where to go next.

## The Plugin Project

A Graph plugin project is a **TypeScript package** — it has a `package.json`, `node_modules`, and TypeScript tooling configured automatically by the Graph CLI — but unlike a typical npm package, it is **not published to a registry**. It is deployed directly to the Graph platform via `graph`.

A single plugin project can contain **many plugins**. All plugins in a project share the same `package.json` and tooling. Each individual plugin lives in its own subdirectory under `src/` with its own `manifest.json` and `plugin.ts`. This makes it easy to co-develop related datatypes, widgets, and nodes together.

## Prerequisites

Before you begin, make sure you have:

* **Node.js** v22 or later — Check your version with `node --version`
* **pnpm** package manager — Install globally with `npm install -g pnpm`
* A code editor (VS Code recommended)
* Basic TypeScript knowledge — You should be comfortable with interfaces, async/await, and basic types

## Project Structure

A Graph plugin project follows a consistent directory layout. The `graph` CLI toolchain handles most configuration automatically — you focus on writing a `manifest.json` and `plugin.ts` for each plugin:

```text
my-plugins/
├── src/
│   ├── node-add/                     ← one directory per plugin
│   │   ├── manifest.json             ← plugin metadata and dependencies
│   │   ├── plugin.ts                 ← plugin implementation
│   │   └── .plugin-dependencies/    ← generated by graph install
│   └── node-multiply/               ← many plugins can share one project
│       ├── manifest.json
│       ├── plugin.ts
│       └── .plugin-dependencies/
├── dist/                             ← generated by graph build
├── package.json                      ← shared tooling config
└── node_modules/
```

## Tutorial: Build Your First Plugin

Let's build a simple "Add Numbers" node. It will have two number inputs and one output that shows their sum. This might seem basic, but it demonstrates all the core concepts you need to build more complex plugins.

### Step 1: Set Up the Project

First, create the directory structure for your plugin project:

```bash
mkdir -p my-plugins/src/node-add
cd my-plugins
```

Now create the `package.json` at the root of your project. This provides the Node.js package environment for the project's tooling:

```json
{
  "name": "my-plugins",
  "version": "1.0.0",
  "type": "module",
  "devDependencies": {
    "@graph/graph-plugin-types": "^2.1.5", // versions may need updating to latest
    "@graph/platform-exports": "^2.2.10",
    "typescript": "^6.0.3"
  }
}
```

### Step 2: Write the Plugin Manifest

Now let's create the plugin's manifest. This is the metadata that describes your plugin to the platform.

Create `src/node-add/manifest.json`:

```json
{
  "name": "@adobe/node-add",
  "version": "1.0",
  "platformVersion": 1,
  "type": "node",
  "assets": {
    "internal": {},
    "exported": {}
  },
  "dependencies": {
    "@adobe/datatype-number": { "majorVersion": 1 },
    "@adobe/widget-number": { "majorVersion": 1 }
  }
}
```

Let's understand what each field means:

* **name** — Your plugin's unique identifier. By convention, use `@yourcompany/plugin-name`.
* **version** — Your plugin's version. Use semantic versioning.
* **platformVersion** — Which version of the Graph platform API this plugin targets. Currently always `1`.
* **dependencies** — Other plugins your plugin needs. Our add node depends on `datatype-number` (for number values) and `widget-number` (for number input UI).

<InlineAlert variant="info" slots="text"/>

**About dependencies:** The platform automatically loads all dependencies before your plugin runs. You declare the major version you need, and the platform ensures compatibility.

### Step 3: Write the Plugin Code

Now for the fun part — let's write the actual plugin code!

Create `src/node-add/plugin.ts`:

```typescript
import { createNodePlugin } from "@graph/platform-exports/v1/node-plugin.js";

export default createNodePlugin({
    displayName: "Add Numbers",
    description: "Adds two numbers together",
    tags: ["category:math", "arithmetic", "add"],
    inputPorts: [
        { name: "a", type: "@adobe/datatype-number", displayName: "A", defaultValue: 0 },
        { name: "b", type: "@adobe/datatype-number", displayName: "B", defaultValue: 0 }
    ],
    outputPorts: [
        { name: "result", type: "@adobe/datatype-number", displayName: "Result" }
    ],
    portWidgetBinding: (inputs, _outputs) => ({
        inputPorts: {
            a: { type: "@adobe/widget-number", data: { value: inputs.a } },
            b: { type: "@adobe/widget-number", data: { value: inputs.b } }
        }
    }),
    process: async (inputs, _context) => {
        return { result: inputs.a + inputs.b };
    }
});
```

Let's walk through each part of this code:

#### Basic Metadata

* **displayName** — What users see in the node catalog when browsing for nodes to add.
* **description** — A short explanation of what the node does. Keep it clear and concise.
* **tags** — Help users find your node. Use `category:` prefix for categories (like `category:math`), then add other descriptive tags.

#### Ports

* **inputPorts** — Define what data flows INTO your node. Each port has:
  * `name` — Internal identifier (use camelCase)
  * `type` — The datatype plugin ID that defines what kind of data this port accepts
  * `displayName` — What users see (use Title Case)
  * `defaultValue` — The initial value if nothing is connected
* **outputPorts** — Define what data flows OUT of your node. Same structure as inputs, but no default values (outputs are computed).

#### Widget Binding

The `portWidgetBinding` function determines what UI appears on each port. It receives the current input values and returns widget configurations:

```typescript
portWidgetBinding: (inputs, _outputs) => ({
    inputPorts: {
        a: { type: "@adobe/widget-number", data: { value: inputs.a } },
        b: { type: "@adobe/widget-number", data: { value: inputs.b } }
    }
})
```

This says: "For input port `a`, show a number widget with the current value. Same for port `b`." Users can click these widgets to edit the values inline.

#### Process Function

The `process` function is where the magic happens. It receives the input values and returns the output values:

```typescript
process: async (inputs, _context) => {
    return { result: inputs.a + inputs.b };
}
```

The platform calls this function whenever the inputs change. It's async because many nodes do asynchronous work (API calls, file I/O, etc.), but our simple math node doesn't need that.

<InlineAlert variant="success" slots="text"/>

**Type Safety:** TypeScript will infer the types of `inputs` and the return value based on your port definitions. If you try to access `inputs.c` or return `{ wrong: 123 }`, you'll get a compile error.

### Step 4: Install Dependencies

Run `graph install` to set up TypeScript for each plugin and link dependency types so your editor can resolve them:

```bash
graph install
```

This creates `.plugin-dependencies/` symlinks so your editor can resolve dependency types. It runs automatically when you run `graph build`, but run it manually after adding a new plugin or changing a plugin's dependencies to keep your editor in sync.

### Step 5: Build

Now let's build the plugin. First, install npm dependencies:

```bash
pnpm install
```

Then build:

```bash
graph build
```

Here's what happens during the build:

1. The build tool scans `src/` for plugin directories (any folder containing a `manifest.json`)
2. For each plugin, it reads the `manifest.json` to understand dependencies
3. It sets up TypeScript and links dependency types
4. It compiles your TypeScript code to JavaScript
5. It outputs everything to the `dist/` directory

If everything worked, you should see output like:

```text
✓ Built @adobe/node-add
✓ Build complete
```

### Step 6: Run the Dev Server

Now for the moment of truth — let's run your plugin in the Graph Editor:

```bash
graph dev
```

This starts a development server with hot-reload. The server will:

1. Load your plugin automatically
2. Watch for changes to your source files
3. Rebuild and reload whenever you save

<InlineAlert variant="info" slots="text"/>

**Connect to dev server!** To connect to the dev server, open up the Graph Editor, then append `?dev=true` to the URL

In the Graph Editor, open the node catalog (click the "+" button or press `/`), search for "add", and you should see your "Add Numbers" node. Drag it onto the canvas, set some values, and watch it compute the sum!

<InlineAlert variant="success" slots="text"/>

**Faster dev cycles:** You can target specific plugins to speed up rebuilds: `graph dev @adobe/node-add`. This only watches and rebuilds the specified plugin.

## Understanding What You Built

Let's recap what we've learned:

* You created a **node plugin** that performs a simple computation
* The node has **typed ports** — inputs and outputs with defined datatypes (`@adobe/datatype-number`)
* **Widget bindings** provide inline editing UI on the ports using `@adobe/widget-number`
* The **process function** is where the actual computation happens — it receives inputs and returns outputs
* The **manifest** declares dependencies so the platform knows what to load before running your plugin

This pattern — ports with types, widget bindings, and a process function — is the foundation of *every* node in the Graph platform. Whether you're building an AI model wrapper, an image processor, or a data transformer, you'll follow this same structure.

## Reference

### Adding More Plugins

For each new plugin, create two files and run one command:

**Step 1 — Create `src/{plugin-name}/manifest.json`** with the plugin metadata (see Manifest Reference below).

**Step 2 — Create `src/{plugin-name}/plugin.ts`** with the plugin implementation.

**Step 3 — Run `graph install`** to set up TypeScript and link dependency types for the new plugin.

The CLI automatically discovers the new plugin by scanning `src/` — no further registration required.

### Manifest Reference

Each plugin declares its metadata and dependencies in a `manifest.json`. The structure is the same for all plugin types — the only differences are the `name` convention and what goes in `dependencies`.

#### Datatype Manifests

Datatypes are foundational types with no plugin dependencies:

```json
{
    "name": "@adobe/datatype-example",
    "version": "1.0",
    "platformVersion": 1,
    "dependencies": {}
}
```

#### Widget Manifests

Widgets provide UI for specific datatypes and must declare datatype dependencies:

```json
{
    "name": "@adobe/widget-example",
    "version": "1.0",
    "platformVersion": 1,
    "dependencies": {
        "@adobe/datatype-example": { "majorVersion": 1 }
    }
}
```

#### Node Manifests

Nodes implement graph operations and typically depend on both datatypes and widgets:

```json
{
    "name": "@adobe/node-example",
    "version": "1.0",
    "platformVersion": 1,
    "dependencies": {
        "@adobe/datatype-example": { "majorVersion": 1 },
        "@adobe/widget-example": { "majorVersion": 1 }
    }
}
```

#### Utility Manifests

Utilities export shared code and must declare `"type": "utility"` along with an `"assets"` block listing each exported module:

```json
{
    "name": "@adobe/utility-example",
    "version": "1.0",
    "platformVersion": 1,
    "type": "utility",
    "assets": {
        "internal": {},
        "exported": {
            "math": "./math.js",
            "helpers": "./helpers.js"
        }
    },
    "dependencies": {}
}
```

For single-file utilities, `assets.exported` can be an empty object `{}`. For multi-file utilities, each additional `.ts` source file must have a corresponding entry mapping its export name to its compiled `.js` bundle path. See [Developing Utilities](../developing-utilities/index.md) for the full guide.

Every datatype and widget referenced in your `plugin.ts` must also appear in the `manifest.json` dependencies.

### Plugin Entry Point (plugin.ts)

Each `plugin.ts` exports a default plugin configuration created by one of the platform-provided factory functions:

* `createDatatypePlugin()` — for datatypes
* `createWidgetPlugin()` — for widgets
* `createNodePlugin()` — for nodes
* `createUtilityPlugin()` — for utilities

These are imported from `@graph/platform-exports/v1/`:

```typescript
import { createDatatypePlugin } from "@graph/platform-exports/v1/datatype-plugin.js";
import { createWidgetPlugin } from "@graph/platform-exports/v1/widget-plugin.js";
import { createNodePlugin } from "@graph/platform-exports/v1/node-plugin.js";
import { createUtilityPlugin } from "@graph/platform-exports/v1/utility-plugin.js";
```

### Common Pitfalls

| Pitfall | Symptom | Fix |
|---|---|---|
| Manifest dependency mismatch | Type errors or runtime errors | Every referenced type/widget must be in `manifest.json` dependencies |
| Missing `as const` on widget data | Type inference breaks on `WidgetElement<typeof data>` | Always add `as const` to the widget data object |
| Stale dependency links | Build warnings, incorrect type resolution | Re-run `graph install` |
| Dev server not picking up new dirs | New plugin doesn't appear | Restart `graph dev` when adding new plugin directories |
| Missing `"type": "utility"` in manifest | Runtime error — platform cannot identify plugin type | Add `"type": "utility"` to the utility's `manifest.json` |
| Exported module not in `assets.exported` | Import fails at runtime; module not bundled | Add an entry to `assets.exported` mapping the module name to its `.js` path |
| Custom `eslint.config.mjs` without `eslint` in `package.json` | `graph lint` throws "ESlint v~9.39.0 required" | Add `eslint: 9.39.4` to `devDependencies` in `package.json` |

### Build Output

The build process:

1. Scans `src/` for plugin directories containing `manifest.json`
2. Sets up TypeScript and links dependency types for each plugin
3. Generates `api-manifest.json` in each plugin's dist directory
4. Outputs compiled JavaScript to `dist/{plugin-name}/`

The `dist/` directory should be gitignored — it contains only build artifacts that are regenerated on each build.
